## 一、官方推荐的开发循环

**来源**: code.claude.com/docs/en/best-practices, code.claude.com/docs/en/common-workflows

官方四步循环：

```
Explore → Plan → Implement → Commit
```

### Phase 1: Explore
- 进入 Plan Mode（Shift+Tab 两次）
- Claude 只读文件、回答问题，不做修改
- 示例 prompt："read /src/auth and understand how we handle sessions and login"

### Phase 2: Plan
- 让 Claude 创建详细实施方案
- Ctrl+G 可在编辑器中打开 plan 直接编辑
- 示例 prompt："I want to add Google OAuth. What files need to change? Create a plan."

### Phase 3: Implement
- 切回 Normal Mode，让 Claude 按 plan 编码
- 官方示例中包含测试："implement the OAuth flow from your plan. write tests for the callback handler, run the test suite and fix any failures."

### Phase 4: Commit
- 让 Claude 提交并创建 PR
- 示例："commit with a descriptive message and open a PR"

**何时跳过 Plan**：
> "If you could describe the diff in one sentence, skip the plan."

**适用 Plan 的场景**：方向不确定、改多个文件、不熟悉的代码区域

## 二、Boris Cherny（Claude Code 创造者）的实际工作流

**来源**: InfoQ, Pragmatic Engineer, VentureBeat, Threads

### 日常流程
- 同时运行 5 个本地终端 + 5-10 个网页会话
- 每个本地会话使用独立的 git checkout，避免冲突
- 约 10-20% 的并行会话因意外场景被放弃

### 开发节奏
1. **Plan Mode 先行**：反复迭代 plan 直到满意
2. **切换到 Auto-Accept**：Claude 通常"一次到位"实现
3. **code-simplifier subagent**：主工作完成后跑代码简化
4. **verify-app subagent**：端到端验证
5. **`/commit-push-pr`**：自定义 slash command，每天用几十次

### 关键原则
- **给 Claude 反馈回路**（测试/浏览器/截图）可提升最终质量 **2-3x**
- 官方原话："Include tests, screenshots, or expected outputs so Claude can check itself. **This is the single highest-leverage thing you can do.**"
- 团队共享 CLAUDE.md 在 git 中，每当 Claude 犯错就添加条目
- 工程师聚焦代码 review 和方向把控；代码以 PR 形式到达，质量已经很好

## 三、社区验证的开发模式

### Explore→Plan→Clear→Code 模式

**来源**: claudecode101.com, codewithmukesh.com, 多个社区博客

社区已广泛采用此模式，claudecode101.com 专门文档化。

**四个阶段**：
1. **Explore**：Plan Mode 启动只读 Explore Subagent 搜索代码库
2. **Plan**：Claude 提问澄清，然后创建结构化 plan.md
3. **Clear/Document**：大型任务中 Claude 将 plan 和进度写入 .md，然后 /clear
4. **Code**：切到 auto-accept 模式，Claude 从 plan 实现

**关键共识**：Explore + Plan 是 token 成本最低、产出价值最高的阶段。

### 官方 Interview Pattern

官方通过 "interview" 模式支持 Clear→Code：

```
"I want to build [brief description]. Interview me in detail using the AskUserQuestion tool.
Keep interviewing until we've covered everything, then write a complete spec to SPEC.md."
```

> "Once the spec is complete, start a fresh session to execute it. The new session has clean context focused entirely on implementation, and you have a written spec to reference."

## 五、测试与验证实践

### 官方推荐

- 提供验证标准：不说"写个验证邮箱的函数"，而是"写 validateEmail 函数，测试用例：user@example.com → true, invalid → false，实现后跑测试"
- 用 PostToolUse hooks 自动跑 linter/type-checker/测试
- 用 subagent 做实现后的 review："use a subagent to review this code for edge cases"
- 用 Chrome 扩展做 UI 视觉验证

### 社区验证层级

```
1. 自验证（Self-verification）   ← Code 阶段，Claude 跑测试验证自己的实现
2. 预提交验证（Pre-commit）      ← Hook 强制 lint + type check + test
3. 代码审查（Review）            ← /simplify + 人工 review
4. CI 验证（Pipeline）           ← 自动化测试 + 安全扫描
5. 生产验证（Production）        ← 监控 + 可观测性
```

### Pre-commit 质量流程（3 步）

1. **构建验证**：TypeScript 类型检查等
2. **测试验证**：防止行为回归
3. **模式验证**：检测禁止的模式（console.log、硬编码密钥等）

## 六、TDD 与 Claude Code

### 核心挑战
Claude 天然倾向"先写实现再写测试"，需要显式要求 TDD。

### Red-Green-Refactor 循环
1. **RED**：写一个失败的测试
2. **GREEN**：写最少代码让测试通过
3. **REFACTOR**：所有测试通过后，清理重复和简化

### 实践方式
- **CLAUDE.md 配置**：嵌入 TDD 规则到 CLAUDE.md
- **自定义 TDD Skill**：定义阶段门禁，阻止在未完成 TDD 步骤时前进（设置成本约 2 小时）
- **多代理 TDD（上下文隔离）**：测试编写者和实现者分离上下文，防止测试被实现思路污染
- **PostToolUse hooks**：每次文件编辑后自动跑测试，即时 Red/Green 反馈
- **TDD Guard**：Hook 系统，阻止 Claude 在没有对应失败测试的情况下写实现代码

### 最适合 TDD 的场景
- 有明确需求的新功能
- Bug 修复（先写复现 Bug 的测试）
- 复杂业务逻辑
- API 契约开发

## 七、确保代码架构质量（高内聚低耦合）

### 已知问题
Claude 有时会：重复代码而不用基类、不重构为共享方法、把过多逻辑塞到一个文件。

### 社区预防策略

1. **Index 文件作为公共 API**：每个 feature 用 index.ts 导出公共接口，创建清晰边界
2. **CLAUDE.md 架构规则**：嵌入 SOLID 原则、设计模式、项目惯例
3. **主动重构 prompt**：让 Claude 拆分大函数、找重复代码提取为工具函数
4. **code-simplifier subagent**：Boris Cherny 在主工作完成后跑代码简化
5. **Spec-driven development**：架构在 Plan 阶段声明，防止架构偏移

### Trail of Bits 的 CLAUDE.md 模板（金标准参考）
- 开发哲学：不做投机性功能、不做过早抽象、替换而非废弃、清晰优于聪明
- 代码质量硬限制：函数长度、复杂度、行宽
- 测试方法和代码 review 顺序
- 工作流规范：commit、hooks、PR

## 八、Spec-Driven Development（规范驱动开发）

**来源**: GitHub Blog, github/spec-kit

GitHub 开源了 "Spec Kit"，支持 Claude Code/Copilot/Gemini/Cursor/Windsurf。

四个门控阶段：
1. **Specify**：描述目标和用户旅程
2. **Plan**：声明架构和约束
3. **Tasks**：拆分为小的、可审查的单元
4. **Implement**：根据 spec 生成代码

核心思想：spec 是 AI 代理生成、测试、验证代码的唯一真相来源，防止"vibe coding"偏移。

## 九、上下文管理最新实践

### /compact vs /clear

| 方式 | 效果 | 适用场景 |
|------|------|---------|
| `/clear` | 完全清空对话历史，保留 CLAUDE.md 和 MEMORY.md | 切换任务、对话过长导致 agent 混乱 |
| `/compact` | 有损压缩，70k token 对话约压缩到 4k | 中途想继续但需要释放空间 |
| `/rewind` + Summarize | 从某个时间点压缩，保留之前的上下文 | 精确控制保留内容 |

### 官方规则
> "If you've corrected Claude more than twice on the same issue in one session, the context is cluttered with failed approaches. Run `/clear` and start fresh with a more specific prompt."

### Auto-compaction
- 自动压缩缓冲区约 33,000 tokens（16.5%）
- 先清除旧的工具输出，再总结对话
- 可在 CLAUDE.md 中添加 "Compact Instructions" 控制保留内容

## 与当前 guides 的差距分析

### 当前 guides 覆盖
- 五步循环：Explore → Plan → Code → Simplify → Commit ✅
- 上下文管理（Document-and-Clear）✅
- 反模式 ✅
- ROADMAP 进度跟踪 ✅
- /spec 讨论成果整理 ✅

### 缺口

1. **验证步骤缺失**：Code 步骤中只有"先写测试 → 实现 → 跑测试"的简单描述，没有企业级验证标准（边界条件、回归测试、类型检查、安全检查等）

2. **"Code 完成标准"未定义**：没有告诉 Claude "功能完成"意味着什么——不是"代码写完了"，而是"代码写完 + 测试通过 + lint 通过 + 边界条件覆盖 + 不影响现有功能"

3. **Explore→Plan→Clear→Code 未作为主动策略推荐**：只在上下文管理中提到 Document-and-Clear 作为被动应对，没有作为复杂功能的推荐开发模式

4. **复杂度判断标准缺失**：没有告诉用户何时走简单流程、何时走完整流程

5. **TDD 未提及**：作为企业级开发的重要实践，guides 中完全没有

6. **CLAUDE.md 行为规范示例缺失**：没有展示如何通过 CLAUDE.md 驱动 Claude 的"一条龙"行为（Code → Verify → Simplify → Commit 连续执行）

7. **Boris Cherny 的 subagent 验证模式未提及**：code-simplifier + verify-app subagent 是已验证的高效模式

#### 1.2 Markdown-based Roadmap 与 Git 活动关联（社区实践 + 我的推断）

对于我们使用的 markdown-based roadmap（`docs/roadmap/` 目录），有以下联动方案：

**方案 A：Claude Code Stop Hook 自动更新（推荐）**

利用 Claude Code 的 `Stop` Hook，在每次任务完成时自动更新 ROADMAP.md：

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "prompt",
            "prompt": "Check if any ROADMAP.md checkbox items were completed in this session. If so, update the checkbox from [ ] to [x] with today's date."
          }
        ]
      }
    ]
  }
}
```

**优点**: 零额外工具，完全在 Claude Code 生态内
**缺点**: 依赖 Claude 判断准确性，可能误更新

**方案 B：Conventional Commits + GitHub Action 解析**

通过 commit message 中的 scope 标记关联 roadmap item：

```
feat(roadmap:auth): implement OAuth2 login flow
fix(roadmap:db): resolve connection pool leak
```

GitHub Action 解析 commit message，自动更新对应的 markdown checkbox：

```yaml
on:
  push:
    branches: [main]
jobs:
  update-roadmap:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Parse commit and update roadmap
        run: |
          # 解析 commit message 中的 roadmap:xxx scope
          # 更新对应 markdown 文件的 checkbox
      - uses: stefanzweifel/git-auto-commit-action@v5
        with:
          commit_message: "docs: auto-update roadmap progress"
```

**来源**: [stefanzweifel/git-auto-commit-action](https://github.com/stefanzweifel/git-auto-commit-action), [markdown-autodocs](https://github.com/marketplace/actions/markdown-autodocs)

**方案 C：/handoff Skill 中的 ROADMAP 同步（我们已采用）**

在 `/handoff` skill 中显式要求 Claude 更新 roadmap：

```markdown
## handoff 步骤
1. 总结本次完成的工作
2. 更新 docs/roadmap/ 中对应的 checkbox（[ ] → [x] 加日期）
3. 生成 HANDOFF.md
```

**来源**: [petekp/claude-code-setup handoff](https://playbooks.com/skills/petekp/claude-code-setup/handoff), [ykdojo/claude-code-tips handoff](https://playbooks.com/skills/ykdojo/claude-code-tips/handoff)

**方案 D：GitHub Markdown Checklist 原生关联（官方功能）**

GitHub Flavored Markdown 支持 checklist 引用 Issue，当 Issue 被关闭时自动标记完成：

```markdown
- [ ] #123 实现用户认证
- [ ] #124 数据库优化
```

Issue #123 关闭后，checklist 自动变为 `[x]`。

**来源**: [GitHub Markdown Checklist Guide](https://www.pullchecklist.com/posts/ultimate-guide-github-markdown-checklist-project-management)

#### 1.3 推荐组合（我的推断，基于社区实践综合）

对于我们的 markdown-based 系统，推荐分层方案：

| 层级 | 机制 | 触发方式 |
|------|------|---------|
| **会话级** | `/handoff` skill 更新 roadmap checkbox | 每次 handoff 时 |
| **提交级** | Conventional commits scope 标记 + CI 解析（可选） | 每次 push 时 |
| **项目级** | 定期 `/catchup` 检查 roadmap 与代码一致性 | 手动触发 |

#### 2.3 Keep-a-changelog vs Auto-generated 的取舍

| 维度 | Keep-a-changelog（手写） | Auto-generated（自动） | 混合方案（推荐） |
|------|------------------------|---------------------|----------------|
| **质量** | 最高：人类审视大局 | 可能是 git log dump | 自动生成 + 人工审核 |
| **成本** | 高：需要手动维护 | 低：自动化 | 中等 |
| **一致性** | 可能遗漏 | 完整不遗漏 | 完整 + 可读 |
| **可读性** | 为人类优化 | 取决于 commit 质量 | 较好 |

**社区共识**: "纯自动生成的 changelog 往往质量较差，但比没有好。最佳方案是使用 Conventional Commits 保证 commit message 质量，然后用工具自动生成初稿，人工审核后发布。"

**Hacker News 上的经典讨论**: "Nobody needs a dump of git log with SHA1 hashes and useless commit titles in a separate text file."

**推荐做法（我的推断，基于社区共识综合）**:

1. 强制 Conventional Commits 格式（通过 commitlint + husky）
2. 用 git-cliff 或 release-please 自动生成 CHANGELOG.md 初稿
3. 每个 PR 要求包含 changelog entry（unreleased section）
4. 发版时人工审核并润色

**来源**: [Keep a Changelog](https://keepachangelog.com/en/1.0.0/), [Common Changelog](https://common-changelog.org/), [Depfu Blog: Changelogs to write or generate](https://depfu.com/blog/changelogs-to-write-or-to-generate)

## Part B: 文档规范

### 四、AI 协作中的文档标准

#### 4.1 CLAUDE.md 中的文档规则（社区实践汇总）

根据对多个企业级 CLAUDE.md 的调研，以下是常见的文档规则：

**通用规则（高频出现）**:

```markdown
## 文档规范

### 代码注释
- 注释解释 "为什么"（why），而非 "做什么"（what）
- 复杂算法必须有注释说明思路和时间复杂度
- TODO 注释必须包含 issue 链接或负责人
- 禁止注释掉的代码（应删除，git 有历史记录）

### API 文档
- 所有公开 API 必须有 JSDoc/docstring
- @param 和 @returns 必须标注类型和描述
- 包含至少一个使用示例
- 标注可能抛出的异常

### 文件头注释
- 每个文件顶部说明其职责和在架构中的位置
- 复杂模块需要说明设计决策的 why
```

**TypeScript/JavaScript 项目常见**:

```markdown
### TypeScript 文档规范
- 使用 JSDoc/TSDoc 注释所有导出的 class、method、interface、type
- @param 使用 `{Type} name - description` 格式
- @returns 说明返回值含义，不只是类型
- @throws 列出可能的异常
- @example 提供至少一个使用示例
- interface 的每个字段都需要 @description
```

**Python 项目常见**:

```markdown
### Python 文档规范
- 使用 Google Style docstring
- 包含 Args, Returns, Raises 三个标准段落
- 类级别 docstring 说明职责和使用场景
- 模块级别 docstring 说明模块在架构中的角色
```

**来源**: [Creating the Perfect CLAUDE.md](https://dometrain.com/blog/creating-the-perfect-claudemd-for-claude-code/), [Writing a Good CLAUDE.md](https://www.humanlayer.dev/blog/writing-a-good-claude-md), [Claude Code Best Practices](https://code.claude.com/docs/en/best-practices), [Comment Directives for Claude Code](https://giuseppegurgone.com/comment-directives-claude-code)

#### 4.2 AI 生成的代码注释质量标准（2026 行业共识）

**核心问题**: AI 生成的注释往往解释 "what"（代码做什么），而忽略 "why"（为什么这样做）。2026 年的行业数据显示：

| 指标 | 数据 | 来源 |
|------|------|------|
| 使用 AI 写文档的开发者比例 | 64% | Google Cloud DORA 2025 |
| 主要使用 AI 写文档的开发者 | 24.8% | Stack Overflow 2025 |
| 部分使用 AI 写文档的开发者 | 27.3% | Stack Overflow 2025 |

**质量控制最佳实践（官方推荐 + 社区实践）**:

1. **AI 生成初稿 + 人工补充 "why"**: AI 擅长生成参数描述、类型说明、示例代码；人工负责补充业务逻辑、设计决策、边界条件原因
2. **模板驱动**: 创建文档模板（style/structure guidelines），让 AI 工具遵循统一格式
3. **CI 检查**: 将文档完整性检查纳入 CI/CD pipeline（如 TypeDoc 编译检查、docstring 覆盖率）
4. **与代码同步更新**: 当代码变更时，文档必须同步更新（工具如 Mintlify 可自动检测）

**来源**: [IBM: AI Code Documentation](https://www.ibm.com/think/insights/ai-code-documentation-benefits-top-tips), [Qodo: Code Documentation Best Practices 2026](https://www.qodo.ai/blog/code-documentation-best-practices-2026/), [Graphite: AI Code Documentation Automation](https://graphite.com/guides/ai-code-documentation-automation)

#### 4.3 API 文档自动生成和维护工具（2025-2026）

| 工具 | 类型 | 特点 |
|------|------|------|
| **Mintlify** | 平台 | Anthropic/Cursor/Perplexity 使用，AI 驱动文档，自动从 PR 更新文档 |
| **DocuWriter.ai** | 平台 | 分析代码库自动生成 OpenAPI specs、JSDoc、README |
| **jsdoc-gen** | CLI | 零配置自动添加 JSDoc/TSDoc 到导出函数/类/类型 |
| **CodeDocs AI** | VS Code 扩展 | 支持 JSDoc、TSDoc、Python docstrings、Markdown README |
| **Apidog** | 平台 | AI 驱动的 API 文档生成，支持从 API 设计或现有规范生成文档 |
| **@implement 注释指令** | Claude Code 内置 | 文件中的 `@implement` 注释被 Claude 转化为实现代码 + JSDoc |

**关键趋势**: 2026 年的文档工具不只是"生成"，而是"持续同步"——当代码变更时自动检测并提示更新文档。

**来源**: [AI Documentation Generators 2026](https://www.nxcode.io/resources/news/ai-documentation-generator-2026), [Apidog AI Documentation](https://apidog.com/blog/ai-powered-documentation-solutions/), [CodeDocs AI](https://marketplace.visualstudio.com/items?itemName=greenbelt-dev.codedocs-ai)

#### 5.3 文档作为代码（Docs-as-Code）最新实践（2025-2026）

**核心原则（官方推荐）**:

1. **文档与代码同仓库**: 版本控制一致，PR 同时包含代码和文档变更
2. **CI/CD 集成**: 文档构建和部署纳入自动化流水线
3. **Review 流程**: 文档变更和代码变更一样需要 review
4. **自动化检查**: Markdown lint、链接检查、拼写检查

**2026 新趋势（社区实践）**:

1. **文档是"完成定义"的一部分**: PR 没有文档更新 = 功能未完成
2. **AI 检测文档-代码不一致**: 当代码变更时，AI 工具提示哪些文档需要更新
3. **元数据丰富的文档**: 文档包含足够的元数据（标签、关联 issue、更新日期），方便 LLM 检索和引用
4. **可分块（chunkable）文档**: 文档结构便于 LLM 理解，每个段落自包含

## 总结与建议

### Part A 总结：Roadmap-Commit 联动方案

**适合我们 markdown-based 系统的推荐方案**（优先级排序）:

1. **已实现 + 优化**: `/handoff` skill 中的 roadmap checkbox 更新（强化格式规范）
2. **低成本新增**: Conventional Commits 规范（`feat(roadmap:xxx):` scope），CLAUDE.md 中添加 commit message 格式要求
3. **可选增强**: Stop Hook + prompt 类型，每次任务结束自动检查 roadmap 更新
4. **可选增强**: git-cliff 自动生成 CHANGELOG.md，release-please 管理版本号

### Part B 总结：文档规范建议清单

**可直接加入 CLAUDE.md 模板或 guides 的规范**:

```markdown
## 文档规范

### 注释原则
- MUST: 注释解释 "为什么"（why），代码本身说明 "做什么"（what）
- MUST: 复杂逻辑、非显而易见的决策必须有注释
- MUST: TODO/FIXME 注释必须关联 issue 编号
- MUST NOT: 禁止保留被注释掉的代码块
- MUST NOT: 禁止无意义的重复性注释（如 `// 设置 name` → `this.name = name`）

### API 文档
- MUST: 所有公开 API（exported function/class/interface）必须有 JSDoc/docstring
- MUST: 包含 @param（类型 + 描述）、@returns（含义）、@throws（异常）
- SHOULD: 包含 @example 使用示例
- Python 使用 Google Style docstring（Args, Returns, Raises）
- TypeScript 使用 TSDoc 格式

### 文件级文档
- MUST: 每个文件顶部说明其职责（一句话）
- SHOULD: 复杂模块说明其在架构中的位置和设计决策

### 文档维护
- MUST: 代码变更必须同步更新相关文档
- MUST: PR 包含文档更新 = 功能完成的一部分
- SHOULD: CHANGELOG 使用 Conventional Commits 驱动自动生成

### Commit Message 规范
- MUST: 遵循 Conventional Commits 格式
- 格式: `<type>(<scope>): <description>`
- 类型: feat | fix | docs | refactor | test | chore | perf | ci
- scope 可选：模块名或 roadmap item 引用
- Breaking changes 用 `!` 标记: `feat!: remove legacy API`
```

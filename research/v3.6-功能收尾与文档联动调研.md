# v3.6 调研报告：功能收尾与文档联动

> **调研日期**: 2026-03-09
> **调研目的**: 功能完成后的收尾流程、Spec 生命周期管理、Roadmap 联动、文档规范
> **调研范围**: Claude Code 官方文档、社区实践、GitHub Spec Kit、Trail of Bits 等企业实践

## 问题 1：功能完成后的自动化收尾

### 关键发现

**1.1 Claude Code 官方无显式 "feature completion" 工作流**

Claude Code 官方文档（code.claude.com）没有一个叫 `/done` 或 `/finish` 的内置命令。官方的设计哲学是通过 Hooks 和 Skills 让用户自定义收尾流程。

- **来源**: [Common workflows - Claude Code Docs](https://code.claude.com/docs/en/common-workflows)、[Best Practices - Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- **分类**: 官方事实

**1.2 Hooks 体系支持收尾自动化，但缺少原生 PostCommit**

Claude Code 当前 Hook 事件包括：`PreToolUse`、`PostToolUse`、`Stop`、`SessionStart`、`SessionEnd` 等。但**没有原生 `PostCommit` 事件**——社区已提出 Feature Request（Issue #4834），当前 workaround 是用 `PostToolUse` + matcher `Bash(git commit:*)` 模拟。

- **来源**: [Hooks Guide](https://code.claude.com/docs/en/hooks-guide)、[GitHub Issue #4834](https://github.com/anthropics/claude-code/issues/4834)
- **分类**: 官方事实 + 社区实践

**1.3 PostToolUse Hook 的文档更新实践**

社区常见模式：用 `PostToolUse` Hook 在文件写入后触发：
- 自动运行 Prettier/Black 格式化
- 自动运行测试套件
- 自动更新 API 文档（jsdoc、sphinx-build）

- **来源**: [DataCamp Hooks Tutorial](https://www.datacamp.com/tutorial/claude-code-hooks)、[GitButler Blog](https://blog.gitbutler.com/automate-your-ai-workflows-with-claude-code-hooks)
- **分类**: 社区实践

**1.4 Addy Osmani 的 2026 工作流建议**

Google 工程师 Addy Osmani 的实践：
- 规划优先、分块迭代，每次只做一个功能
- **2026 目标是强化质量门禁：更多测试、更多监控，甚至 AI-on-AI 代码审查**
- 将 LLM 视为需要明确方向和监督的 pair programmer

- **来源**: [AddyOsmani.com - My LLM coding workflow going into 2026](https://addyosmani.com/blog/ai-coding-workflow/)
- **分类**: 行业专家实践

**1.5 Trail of Bits 企业配置**

安全审计公司 Trail of Bits 开源了他们的 Claude Code 配置：
- 强调"verify before declaring victory"（宣告完成前必须验证）
- Skills 链式执行：brainstorm → plan → execute → verify
- 代码质量硬限制（函数长度、复杂度、行宽）
- "Replace don't deprecate"哲学

- **来源**: [trailofbits/claude-code-config](https://github.com/trailofbits/claude-code-config)
- **分类**: 企业实践

### 可直接应用的建议

1. **新增 `/done` 或 `/wrap-up` Skill**：在现有 `/handoff`（侧重会话切换）之外，新增一个面向"功能完成"的收尾 Skill，执行：
   - 验证所有测试通过
   - 更新 spec 状态 → "已完成"
   - 更新 roadmap checkbox
   - 检查是否需要更新 API 文档 / README
   - 生成 changelog 条目（可选）
   - 运行 `/simplify` 审查

2. **明确区分两种收尾场景**：
   - `/handoff`：会话中断（可能功能未完成），侧重上下文保存
   - `/done`（新增）：功能完成，侧重质量收尾和文档更新

3. **利用 PostToolUse Hook 自动触发文档检查**：当 `git commit` 成功时，提示是否需要更新相关 spec 和 roadmap。

## 问题 2：Spec/设计文档的生命周期管理

### 关键发现

**2.1 GitHub Spec Kit 的五阶段工作流**

GitHub 于 2025 年开源的 Spec Kit 提供了最成熟的 spec 生命周期：
- `/speckit.specify` → 生成 spec.md
- `/speckit.clarify` → 结构化提问补充细节
- Cross-artifact consistency check → 一致性验证
- `/speckit.tasks` → 生成任务列表
- `/speckit.implement` → 指导实现

**关键理念**：Spec 是"可执行的蓝图"（executable blueprint），由三大支柱组成：
- **Intent**（目标：做什么、为什么）
- **Constraints**（约束：技术栈、模式、边界）
- **Acceptance Criteria**（验收标准：具体可测试的条件）

- **来源**: [GitHub Spec Kit](https://github.com/github/spec-kit)、[GitHub Blog](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)
- **分类**: 官方工具（GitHub）

**2.2 Pimzino 的 Spec Workflow 四阶段模型**

社区广泛使用的方案：Requirements → Design → Tasks → Implementation
- 建议用 Opus 4 生成 spec，用 Sonnet 4 执行实现
- 分层上下文管理：主代理加载全部上下文，子代理按需加载
- 开发重心已转向 MCP 版本（更好的可视化和仪表板）

- **来源**: [Pimzino/claude-code-spec-workflow](https://github.com/Pimzino/claude-code-spec-workflow)
- **分类**: 社区实践

**2.3 ADR 最佳实践**

AWS 和微软都推荐 ADR 与代码放一起：
- **存放位置**: 项目内 `docs/architecture/adr/` 目录
- **单一决策原则**: 每个 ADR 只记录一个决策
- **AI 辅助**: LLM 可以端到端简化 ADR（writer → validator → formatter）
- **Decision Guardian**: 新兴工具可在 PR 中自动浮现相关的 ADR

- **来源**: [AWS ADR Process](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)、[AWS Architecture Blog](https://aws.amazon.com/blogs/architecture/master-architecture-decision-records-adrs-best-practices-for-effective-decision-making/)、[ADR Writer Agent](https://piethein.medium.com/building-an-architecture-decision-record-writer-agent-a74f8f739271)
- **分类**: 行业标准 + 社区实践

**2.4 文档生命周期管理的通用模型**

行业通用的文档生命周期为：创建 → 审核 → 批准 → 分发 → 使用 → 更新 → 归档 → 销毁
- 项目文档归档通常在实施后 90 天
- 归档文档保留至少 12 个月
- 归档后可检索但不再主动加载

- **来源**: [Technical Writer HQ](https://technicalwriterhq.com/documentation/document-lifecycle-management/)、[CogniDox](https://www.cognidox.com/blog/what-is-document-lifecycle-management)
- **分类**: 行业标准

### 可直接应用的建议

1. **完善 Spec 状态枚举**：当前系统已有 `草稿 → 已确认 → 实施中 → 已完成`，建议增加：
   - `已归档`：功能上线稳定运行后，spec 不再需要主动参考（减少 token 消耗）
   - 归档规则：功能完成 + 通过一个完整开发周期后自动建议归档

2. **增加 Acceptance Criteria 模块**：借鉴 GitHub Spec Kit 的三支柱结构，在 spec 模板中强制包含"验收标准"——这是 `/done` Skill 判断功能是否完成的依据。

3. **Spec 与 ADR 的关系明确化**：
   - Spec = "做什么"（功能描述，有生命周期，会被归档）
   - ADR = "为什么这样做"（决策记录，永久保留，不归档）
   - 在 spec 中引用相关 ADR 编号

## 问题 3：Roadmap 与代码提交的联动

### 关键发现

**3.1 CCPM (Claude Code Project Manager)**

社区开发的项目管理系统，核心特性：
- Spec-driven：每行代码都可追溯到 spec
- 并行 agent 执行（多个 AI 同时工作）
- GitHub Issues 集成
- 完整审计追踪（从 PRD 到生产）

- **来源**: [automazeio/ccpm](https://github.com/automazeio/ccpm)
- **分类**: 社区工具

**3.2 Claude Code 自定义 Roadmap 命令**

多个社区方案使用自定义 slash command 管理 roadmap：
- `/update-roadmap`：手动触发 roadmap 更新
- checkbox 进度约定：`[ ]` = Todo, `[-]` = In Progress, `[x]` = Completed
- 配合 Playwright MCP 可自动截图记录进度

- **来源**: [arach/claude-roadmap-commands](https://github.com/arach/claude-roadmap-commands)、[Ben Newton Blog](https://benenewton.com/blog/claude-code-roadmap-management)
- **分类**: 社区实践

**3.3 Conventional Commits + 自动 Changelog**

业界成熟方案链：
- **提交规范**: Conventional Commits（`feat(scope): description`）
- **强制执行**: commitlint + husky（git hook）或 Claude Code PreToolUse Hook
- **Changelog 生成**: conventional-changelog-cli、git-cliff、release-please
- **Claude Code 社区 Skill**: 已有 changelog-generator Skill 可分析 commit 历史自动生成用户友好的 release notes
- **最佳 Git 策略**: trunk-based development + PR squash merge 保持历史整洁

- **来源**: [Conventional Commits](https://www.conventionalcommits.org/)、[git-cliff](https://git-cliff.org/)、[ComposioHQ changelog-generator](https://github.com/ComposioHQ/awesome-claude-skills/blob/master/changelog-generator/SKILL.md)
- **分类**: 行业标准 + 社区实践

**3.4 GitHub Projects 自动联动**

GitHub Projects 原生支持：
- PR merge 时自动更新 Issue 状态
- Issue 关联 Roadmap 视图
- 支持自动化规则（当 PR merge → 移动到 Done 列）

- **来源**: [GitHub Docs - Planning and tracking](https://docs.github.com/en/issues/planning-and-tracking-with-projects)
- **分类**: 平台功能

### 可直接应用的建议

1. **在 `/done` Skill 中集成 Roadmap 更新**：功能完成时自动检查并更新 roadmap，目前 `/handoff` 已做了这一步，`/done` 应继承并强化。

2. **建议（不强制）在指南中添加 Changelog 生成模块**：
   - 对于有版本发布需求的项目，推荐 Conventional Commits + release-please
   - 可创建一个 `/changelog` Skill 或在 `/done` 中可选触发

3. **Git Commit Message 规范已有，强化即可**：当前 guides 已推荐 Conventional Commits 格式，可补充 commitlint 集成说明。

## 问题 4：企业级文档规范在 AI 协作中的应用

### 关键发现

**4.1 CLAUDE.md 官方推荐**

Anthropic 官方博客和文档明确推荐：
- CLAUDE.md 是 Claude 的"长期记忆"，每次会话自动读取
- 内容应包括：bash 命令、代码风格、工作流规则、测试指令、仓库约定
- **精简原则**：官方推荐 ≤500 行（SKILL.md），社区实践建议 ≤200 行
- **每条规则应解决实际遇到的问题**，而非理论关切
- 不放敏感信息（API key、密码），因为它会成为系统提示的一部分

- **来源**: [Using CLAUDE.MD files](https://claude.com/blog/using-claude-md-files)、[Writing a good CLAUDE.md](https://www.humanlayer.dev/blog/writing-a-good-claude-md)
- **分类**: 官方推荐

**4.2 企业级 AI 代码治理**

企业采用 AI 编码时需要：
- **使用指南**：明确 AI 适用场景
- **审批流程**：AI 生成代码进入生产的审批路径
- **文档标准**：提供清晰性以支持自信采用
- **层级覆盖机制**：企业策略 > 命令行参数 > 本地配置 > 共享配置 > 全局配置

- **来源**: [getdx.com - AI code enterprise adoption](https://getdx.com/blog/ai-code-enterprise-adoption/)
- **分类**: 行业标准

**4.3 Spec-Driven Development 作为文档标准**

Thoughtworks 2025 年将 SDD 列为关键新兴实践：
- Spec 作为 source of truth（代码是生成/验证的次级产物）
- **何时必须用 SDD**：涉及金钱、安全、权限；他人将长期维护的代码
- 验收标准是"完成"的唯一定义

- **来源**: [Thoughtworks - Spec-driven development](https://thoughtworks.medium.com/spec-driven-development-d85995a81387)、[Red Hat Developer](https://developers.redhat.com/articles/2025/10/22/how-spec-driven-development-improves-ai-coding-quality)
- **分类**: 行业权威实践

**4.4 文档层次建议**

| 层次 | 内容 | 存放位置 | 维护方式 |
|------|------|---------|---------|
| 代码注释 | 函数/类的 why，非 what | 代码文件内 | Claude 自动生成，人工审查 |
| API 文档 | 端点、参数、返回值 | 自动生成（jsdoc/openapi） | PostToolUse Hook 触发更新 |
| Spec 设计文档 | 功能设计、方案决策 | `docs/specs/` | `/spec` 生成，`/done` 收尾 |
| ADR | 架构决策及理由 | `docs/architecture/adr/` | 重大决策时手动创建 |
| Roadmap | 项目进度 | `docs/roadmap/` | `/handoff` `/done` 自动更新 |
| CLAUDE.md | AI 协作规范 | 项目根目录 + 子目录 | 遇到实际问题时添加规则 |

- **分类**: 我的推断（综合多个来源）

### 可直接应用的建议

1. **在指南中明确文档层次体系**：将上表加入 guides，让用户清楚每类文档的定位。

2. **强调"Spec 中必须有验收标准"**：这是 SDD 的核心，也是自动化判断"完成"的依据。

3. **API 文档自动化可作为可选模块**：不是所有项目都需要，但有 API 的项目应在 PostToolUse Hook 中集成文档生成。

## 问题 5：其他可能遗漏的最佳实践

### 关键发现

**5.1 Sub-Agent 成本优化（官方推荐）**

设置 `CLAUDE_CODE_SUBAGENT_MODEL` 环境变量，主会话用 Opus，子代理用 Sonnet，可显著降低成本而不牺牲质量。

- **来源**: [Claude Code Sub-Agent Best Practices](https://claudefa.st/blog/guide/agents/sub-agent-best-practices)
- **分类**: 社区最佳实践（广泛验证）

**5.2 SKILL.md 编写最佳实践**

- description 是关键：Claude 用它从 100+ Skills 中选择正确的 Skill
- 文件大小目标：~150 行，内部最大 200 行；>300 行应拆分为 REFERENCE.md
- 命名建议：动名词形式（verb + -ing），如 "reviewing"、"generating"

- **来源**: [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)、[Claude Skills Guide](https://www.gend.co/blog/claude-skills-claude-md-guide)
- **分类**: 官方推荐

**5.3 `/install-github-app` 自动 PR Review**

Claude Code 内置命令，安装后 Claude 会自动 review 所有 PR——可作为额外的质量门禁。

- **来源**: [Builder.io - How I use Claude Code](https://www.builder.io/blog/claude-code)
- **分类**: 官方功能

**5.4 Agent Teams 已进入 Research Preview**

2026-02 发布，支持多个 Claude 并行工作、git-based 协调、自动冲突解决。当前指南已覆盖此功能。

- **来源**: [Agent Teams Workflow](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/guide/workflows/agent-teams.md)
- **分类**: 官方功能（实验性）

**5.5 "Definition of Done" 在 AI 时代的新含义**

- 传统 DoD：代码 review + 测试通过 + 文档更新
- AI 时代 DoD 增加了：**显式 spec 验证 + 人工审查 AI 生成代码 + 质量门禁自动化**
- 只有约 30% 的 AI 建议代码被开发者接受（GitHub Copilot 数据）
- AI 辅助代码的克隆率是之前的 4 倍——需要更严格的重复检测

- **来源**: [MIT Technology Review](https://www.technologyreview.com/2025/12/15/1128352/rise-of-ai-coding-developers-2026/)、[Thoughtworks SDD](https://thoughtworks.medium.com/spec-driven-development-d85995a81387)
- **分类**: 行业数据 + 我的推断

**5.6 当前 Guides 中的潜在差距**

对比调研结果与现有 guides，发现以下差距：

| 现有覆盖 | 调研发现的差距 |
|---------|--------------|
| 六步开发循环 ✅ | 缺少"功能完成"的显式收尾步骤 |
| `/handoff` ✅ | `/handoff` 是"会话交接"，非"功能完成" |
| Spec 四状态 ✅ | 缺少"已归档"状态和归档规则 |
| Spec 模板 ✅ | 缺少强制性"验收标准"模块 |
| Roadmap ✅ | 缺少与 Changelog 的联动 |
| Conventional Commits ✅ | 缺少 commitlint 集成和 Changelog 自动生成 |
| ADR 目录 ✅ | 缺少 ADR 模板和与 Spec 的关联说明 |
| 文档层次隐含在各文档中 | 缺少统一的文档体系概览 |

## 综合建议：Guides 应新增或修改的内容

### 优先级 P0：新增 `/done` Skill（功能完成收尾）

**理由**：当前 guides 最大的空白是 `Code → Verify → Simplify → Commit` 之后缺少显式的"功能级收尾"。`/handoff` 侧重会话切换，不等于功能完成。

**`/done` Skill 设计草案**：

```
触发时机：一个功能/spec 的全部代码已提交
执行步骤：
1. 验证检查
   - 所有测试通过？
   - lint/type 检查通过？
   - 如有 spec → 逐项检查验收标准是否满足
2. 文档更新
   - Spec 状态 → "已完成"
   - Roadmap checkbox → [x]
   - 检查是否有 API 变更 → 提示更新 API 文档
   - 检查是否有架构决策 → 提示创建 ADR
3. 代码审查
   - 运行 /simplify（如果本次会话还没跑过）
4. 提交文档变更
   - git add docs/ && git commit -m "docs: 更新 [功能名] 完成状态"
5. 输出完成报告
```

### 优先级 P1：完善 Spec 模板

**改动点**：
- 在 spec 模板中增加"验收标准"模块（必填），参考 GitHub Spec Kit 的 Acceptance Criteria
- 增加"已归档"状态到生命周期：`草稿 → 已确认 → 实施中 → 已完成 → 已归档`
- 归档规则：功能完成后的下一个 Phase 完成时，自动建议归档旧 spec
- 明确 Spec vs ADR 的关系和定位

### 优先级 P1：在工作流文档中增加"文档体系概览"

**新增一节**，统一说明项目中各类文档的定位、存放位置、生成方式和维护规则。避免信息分散在多个文档中。

### 优先级 P2：Changelog 自动生成（可选模块）

**改动点**：
- 在 Hooks 或 Skills 文档中增加 Changelog 生成的配置说明
- 推荐 release-please 或 git-cliff
- 可选创建 `/changelog` Skill
- 不强制所有项目都用——仅有版本发布需求的项目

### 优先级 P2：ADR 模板和使用指引

**改动点**：
- 提供 ADR 模板（标题、状态、上下文、决策、后果）
- 说明 ADR 与 spec 的关系
- 推荐在 `/deep-audit` 中检查是否有遗漏的架构决策需要记录

### 优先级 P3：其他小改进

- **子代理模型优化说明**：在 Agent Teams 或子代理章节增加 `CLAUDE_CODE_SUBAGENT_MODEL` 配置
- **`/install-github-app` 提及**：在 CI/CD 或 PR 审查相关章节提到此功能
- **commitlint 集成**：在 Hooks 文档中增加 commitlint 作为 PreToolUse Hook 的可选配置

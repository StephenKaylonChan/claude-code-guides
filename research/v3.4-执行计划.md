**位置**: Section 2 "核心 Hook 事件"

| 事件 | 触发时机 | 典型用途 |
|------|---------|---------|
| `SessionEnd` | 会话终止时 | 清理资源、记录会话统计 |
| `PermissionRequest` | 权限请求时（可阻断） | 编程化自动审批/拒绝权限 |

| `Setup` | --init/--init-only/--maintenance 触发 | 仓库初始化和维护脚本 |

**注意**: 需要重新分类。按照官方文档：
- 支持 command + prompt + agent 的事件：PermissionRequest, PostToolUse, PostToolUseFailure, PreToolUse, Stop, SubagentStop, TaskCompleted, UserPromptSubmit
- 仅支持 command 的事件：ConfigChange, Notification, PreCompact, SessionEnd, SessionStart, SubagentStart, TeammateIdle, WorktreeCreate, WorktreeRemove, Setup

当前我们的分类方式是"支持 matcher / 不支持 matcher"，这和 handler 类型分类不同。需要决定：保持现有分类方式（按 matcher），还是换成官方分类（按 handler 类型）？

**建议**: 保持现有"支持 matcher / 不支持 matcher"分类，在每个事件后面备注支持的 handler 类型。将新事件加到对应分类中。

具体分类：
- **支持 matcher 的事件**（现有）: SessionStart, PreToolUse, PostToolUse, Stop, Notification, PreCompact, SubagentStop
- **支持 matcher 的事件**（新增）: PostToolUseFailure（matcher 匹配工具名）, PermissionRequest（matcher 匹配工具名）
- **不支持 matcher 的事件**（现有）: UserPromptSubmit, InstructionsLoaded, ConfigChange, WorktreeCreate, WorktreeRemove, TeammateIdle, TaskCompleted
- **不支持 matcher 的事件**（新增）: SessionEnd, SubagentStart, Setup

#### 1.2 补充 Async Hooks 说明

**位置**: Section 3 "Handler 类型" 末尾，或 Section 7 "性能注意事项" 中

```markdown
### Async Hooks（异步执行）

2026-01 起，hooks 支持异步执行。在 hook 配置中添加 `"async": true`，hook 将在后台运行，不阻塞 Claude 的执行。

适合场景：
- 通知类 hook（桌面通知、Slack 消息）
- 日志记录
- 不需要即时反馈的后台操作

```json
{
  "type": "command",
  "command": "bash .claude/hooks/on-stop.sh",
  "async": true
}
```

> **注意**: 异步 hook 不能阻断操作（exit code 2 无效），因为 Claude 不会等待其完成。
```

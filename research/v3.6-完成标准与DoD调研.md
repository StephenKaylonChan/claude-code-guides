# Definition of Done (DoD) 在 AI 辅助开发中的实践

> 调研时间：2026年3月 | 信息来源：Claude Code 官方文档、Thoughtworks、Scrum.org、Addy Osmani 等

---

## 一、传统 Definition of Done (DoD) 体系

### 1.1 什么是 Definition of Done

Definition of Done (完成标准) 是 Scrum 框架中的正式承诺，它建立了**每个产品待办事项 (PBI) 和增量 (Increment) 在被视为"完成"之前必须满足的质量标准**。它不仅仅是一个清单，而是整个 Scrum 团队对"完成"含义的共识。

核心特征：
- **普遍适用性**：DoD 统一适用于所有工作项（与 Acceptance Criteria 不同，后者因 Story 而异）
- **不可协商性**：不满足 DoD 的工作不能发布
- **演进性**：随团队能力成熟而不断升级

### 1.2 三层 DoD 模型（传统）

| 层级 | 适用范围 | 典型内容 |
|------|---------|---------|
| **功能级 DoD** | 单个 User Story / PBI | 代码通过 code review、单元测试覆盖率达标、功能测试通过、无已知缺陷 |
| **Sprint 级 DoD** | Sprint Increment | 所有 PBI 满足功能级 DoD、集成测试通过、性能回归测试通过、Sprint Review 演示完成 |
| **Release 级 DoD** | 可发布增量 | 满足 Sprint 级 DoD、安全扫描通过、文档更新完成、部署脚本验证通过、合规性审计完成 |

### 1.3 企业级 DoD 标准参考清单

来自 Scrum.org 和 Atlassian 的综合最佳实践：

```
□ 代码已提交且通过 CI 构建
□ 代码评审已完成（至少一位评审者）
□ 单元测试已编写且覆盖率 ≥ 阈值（通常 80%+）
□ 集成测试通过
□ 无新的静态分析警告（lint/sonar）
□ 安全扫描无高危漏洞
□ 性能基准未退化
□ API 文档已更新
□ CHANGELOG 已更新
□ 产品负责人已验收
□ 可在类生产环境部署
```

## 二、AI 辅助开发中的 DoD 创新

### 2.1 从"人工检查"到"自动执行"的转变

AI 辅助开发（Claude Code、Cursor、Copilot 等）正在改变 DoD 的执行方式。传统 DoD 依赖人工逐项核查，而 AI 时代的 DoD 可以被**编码为自动化规则，由 AI Agent 或 CI/CD pipeline 强制执行**。

| 维度 | 传统 DoD | AI 增强 DoD |
|------|---------|------------|
| **执行方式** | 人工逐项检查 | Agent hooks 自动强制执行 |
| **检查时机** | Sprint 结束时回顾 | 每次 commit / 每次 tool call / task 完成时实时检查 |
| **反馈速度** | 延迟（人工发现问题） | 即时（hook 阻断并给出修复建议） |
| **覆盖范围** | 依赖人的记忆和纪律 | 确定性 100% 覆盖 |
| **规范载体** | Wiki / Confluence 页面 | CLAUDE.md / .cursor/rules / 配置文件 |
| **文档更新** | 手动更新 | 自动生成 changelog、自动更新文档 |
| **质量门禁** | PR review 时讨论 | PreToolUse / Stop / TaskCompleted hooks 自动拦截 |

### 2.2 将 DoD 写入 CLAUDE.md 的实践

越来越多的团队将 DoD 直接嵌入 CLAUDE.md，使 AI Agent 在每次会话中自动遵循完成标准。

**核心理念**：CLAUDE.md 不仅是"项目说明书"，更是 AI Agent 的"行为宪法"——它定义了 Agent 应该如何判断"完成"。

来自社区的实践模式包括：

1. **规则驱动 DoD**：在 CLAUDE.md 中直接声明完成标准，Claude 在每次响应中自动遵循
2. **Spec-Driven Development (SDD)**：先写规格说明，再由 AI 生成代码，规格本身成为 DoD 的一部分
3. **Promise Pattern**：输出特定标记（如 `<promise>DONE</promise>`）仅在所有条件满足时出现

### 2.3 AI Agent 自动执行 DoD 的机制（Claude Code Hooks）

Claude Code 提供了完整的 hook 生命周期系统（截至 2026 年 2 月已有 **17 个生命周期事件**），其中与 DoD 直接相关的关键事件：

| Hook 事件 | 触发时机 | DoD 用途 |
|-----------|---------|---------|
| **`Stop`** | Claude 完成响应时 | 阻止 Claude 停止，强制执行 lint/test/type-check 等质量门禁 |
| **`TaskCompleted`** | 任务被标记为完成时 | 阻止任务关闭，直到测试通过、代码质量达标 |
| **`PostToolUse`** | 工具调用完成后 | 每次文件编辑后自动运行 lint/format |
| **`PreToolUse`** | 工具调用前 | 阻止危险操作（如 `rm -rf`）|
| **`TeammateIdle`** | Agent Team 成员即将空闲时 | 在队友停止前验证其工作质量 |

**TaskCompleted 事件详解**（官方文档）：

```json
// .claude/settings.json
{
  "hooks": {
    "TaskCompleted": [
      {
        "hooks": [
          {
            "type": "command",
            "command": ".claude/hooks/verify-dod.sh"
          }
        ]
      }
    ]
  }
}
```

```bash
#!/bin/bash
# .claude/hooks/verify-dod.sh
INPUT=$(cat)
TASK_SUBJECT=$(echo "$INPUT" | jq -r '.task_subject')

# 运行测试套件
if ! npm test 2>&1; then
  echo "Tests not passing. Fix failing tests before completing: $TASK_SUBJECT" >&2
  exit 2  # exit 2 = 阻断，阻止任务标记为完成
fi

# 运行 lint 检查
if ! npm run lint 2>&1; then
  echo "Lint errors found. Fix before completing: $TASK_SUBJECT" >&2
  exit 2
fi

exit 0  # 所有检查通过，允许任务完成
```

**关键控制机制**：
- **Exit code 2**：阻断动作，stderr 消息作为反馈传递给 AI 模型
- **JSON `{"continue": false, "stopReason": "..."}`**：彻底停止 Agent

**注意**：截至 2026 年 3 月，Claude Code **没有**原生的 `PostCommit` hook 事件（这是社区请求的功能，见 [GitHub Issue #4834](https://github.com/anthropics/claude-code/issues/4834)）。Git commit 后的自动化需要通过 `PostToolUse` 匹配 `Bash` 工具来间接实现，或使用 Git 原生的 post-commit hook。

## 三、功能完成后的自动化动作

### 3.1 Conventional Commits + 自动 Changelog

当前最佳实践链路：

```
Conventional Commits → commitlint (强制格式) → CI/CD → 自动化工具 → CHANGELOG + Release
```

**主流工具对比（2026 年）**：

| 工具 | 特点 | 适用场景 |
|------|-----|---------|
| **semantic-release** | 全自动化版本管理 + 发布；基于 commit messages 自动判断 major/minor/patch | Node.js 生态、npm 包发布 |
| **release-please** | Google 出品；创建 Release PR，人工确认后合并发布 | 需要人工审批的团队 |
| **git-cliff** | 高度可定制的 changelog 生成器；支持任意 Git 仓库 | 多语言项目、自定义格式需求 |
| **python-semantic-release** | Python 生态的 semantic-release | Python 项目 |

**Conventional Commits 格式**：

```
<type>(<scope>): <description>

[optional body]

[optional footer(s)]
```

类型包括：`feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`chore`、`ci`

**在 Claude Code 中强制执行**：可通过 `PostToolUse` hook 在 Bash 工具执行 `git commit` 后验证 commit message 格式。

### 3.2 Post-Merge 自动化

团队在 PR 合并后常见的自动化动作：

| 自动化动作 | 实现方式 | 说明 |
|-----------|---------|------|
| **自动生成 Changelog** | GitHub Actions + semantic-release / git-cliff | 基于 conventional commits 自动更新 CHANGELOG.md |
| **自动发布 Release** | GitHub Actions + release-please | 自动创建 GitHub Release 和 Tag |
| **自动部署** | GitHub Actions on `push: main` | 合并到主分支后自动触发部署流水线 |
| **自动通知** | Slack/Teams webhook | 通知团队新功能已合并 |
| **自动更新文档** | GitHub Actions + 文档生成工具 | API 文档自动从代码注释重新生成 |
| **自动创建下游 Issue** | GitHub Actions | 如触发下游服务的兼容性测试 |

**GitHub Agentic Workflows（2026 年 2 月技术预览）**：
GitHub 推出了 Agentic Workflows，允许用 **Markdown 编写工作流**（而非 YAML），AI Agent 在 GitHub Actions 中执行仓库任务。这为 Post-Merge 自动化提供了新的范式。

### 3.3 在 Claude Code 中实现完成后自动化

利用 `Stop` hook + `TaskCompleted` hook 的组合：

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": ".claude/hooks/on-stop.sh",
            "statusMessage": "Running completion checks..."
          }
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": ".claude/hooks/post-bash.sh",
            "async": true
          }
        ]
      }
    ]
  }
}
```

## 四、Spec-Driven Development：DoD 的未来形态

### 4.1 SDD 核心思路

由 Thoughtworks 在 2025 年提出并推广，SDD 将**规格说明 (Specification) 从文档升级为可执行的验证门禁**：

```
Requirements Spec → Design Spec → Task Breakdown → Implementation → Validation against Spec
```

**与传统 DoD 的关系**：在 SDD 中，Spec 本身就是 DoD——如果实现与 Spec 不一致，就不算完成。

### 4.2 在 Claude Code 中实践 SDD

推荐的工作流（来自 Addy Osmani 2026 年实践）：

1. **先写详细 Spec**（放在 `specs/` 或 `TASKS.md`）
2. **将 Spec 引用写入 CLAUDE.md**，让 Claude 每次会话都能对照
3. **实现后比对**：要求 Claude "对照 Spec 检查所有需求是否满足，列出未覆盖的项"
4. **LLM-as-Judge**：用第二个 Agent 审查第一个 Agent 的输出

## 五、三层完成标准模型（AI 增强版）

基于调研提炼的三层模型，适用于 AI 辅助开发：

### 第一层：Commit 级完成标准

> 每次 commit 自动执行，通过 PostToolUse hook 或 Git pre-commit hook 强制

```
□ 代码通过 lint 检查（无新增警告）
□ 代码通过格式化（prettier / black / gofmt）
□ commit message 符合 Conventional Commits 规范
□ 无硬编码密钥或敏感信息（secret scanning）
□ 受影响文件的单元测试通过
□ TypeScript / 静态类型检查通过（如适用）
```

### 第二层：功能级完成标准

> 功能开发完成时执行，通过 TaskCompleted hook 或 Stop hook 强制

```
□ 满足 Commit 级所有标准
□ 所有 Acceptance Criteria 已实现并验证
□ 完整测试套件通过（npm test / pytest）
□ 测试覆盖率不低于基线（如 ≥ 80%）
□ 前后端接口已对接并验证
□ 错误处理和边界条件已覆盖
□ 无 TODO / FIXME / HACK 残留（或已记录为 Issue）
□ API 变更已更新相关文档
□ 实现与 Spec/需求文档一致（可用 LLM-as-Judge 验证）
□ 对现有功能无回归影响
```

### 第三层：Phase 级完成标准

> Sprint / Milestone / Release 完成时执行，通过 CI/CD pipeline 强制

```
□ 满足功能级所有标准
□ 集成测试通过
□ E2E 测试通过
□ 性能基准测试未退化（Lighthouse perf ≥ 90 或自定义阈值）
□ 安全扫描通过（SAST/DAST/依赖审计）
□ CHANGELOG.md 已更新（自动生成或人工审核）
□ Release Notes 已准备
□ 文档站点已更新部署
□ 可在 staging 环境正常运行
□ 产品负责人已 Review 并签收
□ 回滚方案已准备
```

## 六、可直接写入 CLAUDE.md 的完成标准模板

以下模板可直接复制到项目的 CLAUDE.md 文件中使用：

```markdown
## 完成标准 (Definition of Done)

### Commit 级（每次提交必须满足）
- 代码通过 lint 和格式化检查
- commit message 遵循 Conventional Commits: `<type>(<scope>): <description>`
- 不引入硬编码密钥或临时方案
- 受影响文件的单元测试全部通过
- 静态类型检查通过（如适用）

### 功能级（完成功能开发时必须满足）
- Commit 级所有标准已满足
- 所有 Acceptance Criteria 已实现
- 完整测试套件通过，覆盖率不低于基线
- 前后端接口已对接验证
- 错误处理和边界条件已覆盖
- 无遗留 TODO/FIXME（或已转为 Issue 追踪）
- 相关文档/注释已更新
- 实现与 Spec 一致（逐项核对）

### Phase 级（Sprint/Release 结束时必须满足）
- 功能级所有标准已满足
- 集成测试和 E2E 测试通过
- 性能基准未退化
- 安全扫描无高危漏洞
- CHANGELOG 已更新
- Release Notes 已准备
- 可在 staging 环境正常运行

### 自我检查流程
完成任何功能后，执行以下步骤：
1. 运行 `npm test`（或项目对应的测试命令）确认所有测试通过
2. 运行 `npm run lint` 确认无 lint 错误
3. 对照需求/Spec 逐项确认所有要求已实现
4. 检查是否有遗留的 TODO 或临时代码
5. 确认错误处理是否完善（空值、超时、权限等边界情况）
6. 如有 API 变更，确认文档已同步更新
```

## 七、配套的 Claude Code Hooks 配置模板

将以下配置放入 `.claude/settings.json`，实现 DoD 的自动化强制执行：

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/lint-check.sh",
            "statusMessage": "Running lint check..."
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/stop-quality-gate.sh",
            "statusMessage": "Running quality gate checks..."
          }
        ]
      }
    ],
    "TaskCompleted": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/verify-dod.sh",
            "statusMessage": "Verifying Definition of Done..."
          }
        ]
      }
    ]
  }
}
```

**stop-quality-gate.sh 示例**：

```bash
#!/bin/bash
# .claude/hooks/stop-quality-gate.sh
# 在 Claude 完成响应前运行质量门禁

INPUT=$(cat)
STOP_HOOK_ACTIVE=$(echo "$INPUT" | jq -r '.stop_hook_active // false')

# 防止无限循环：如果已经在 stop hook 中，直接放行
if [ "$STOP_HOOK_ACTIVE" = "true" ]; then
  exit 0
fi

ERRORS=""

# 检查测试
if ! npm test --silent 2>&1; then
  ERRORS="${ERRORS}\n- Tests are failing"
fi

# 检查 lint
if ! npm run lint --silent 2>&1; then
  ERRORS="${ERRORS}\n- Lint errors found"
fi

# 检查 TypeScript 编译（如适用）
if [ -f "tsconfig.json" ]; then
  if ! npx tsc --noEmit 2>&1; then
    ERRORS="${ERRORS}\n- TypeScript compilation errors"
  fi
fi

if [ -n "$ERRORS" ]; then
  echo '{"decision": "block", "reason": "Quality gate failed:'"$ERRORS"'"}'
  exit 0
fi

exit 0
```

## 八、关键发现与建议

### 8.1 行业趋势

1. **Spec-Driven Development 成为主流**：Thoughtworks 将其列入 2025 Technology Radar，预期 2026 年进一步普及。SDD 模糊了"需求文档"和"完成标准"的边界。

2. **Hook 驱动的确定性质量门禁**：与依赖 LLM 自主判断不同，Hooks 提供了确定性的控制——"确保某些动作总是发生，而不是依赖 LLM 选择去执行它们"（Claude Code 官方文档）。

3. **LLM-as-Judge**：Addy Osmani 提出的模式——用第二个 Agent 审查第一个 Agent 的输出。这为难以自动化测试的质量维度（如代码可读性、架构合理性）提供了新的检查方式。

4. **GitHub Agentic Workflows（2026 年 2 月技术预览）**：用 Markdown 编写 CI/CD 工作流，AI Agent 直接在 GitHub Actions 中运行。这可能重塑 Post-Merge 自动化的方式。

### 8.2 实施建议

1. **从 CLAUDE.md 开始**：先将 DoD 写入 CLAUDE.md，让 AI 在对话中自觉遵循
2. **逐步添加 Hooks**：从 `PostToolUse` (lint) 开始，逐步添加 `Stop` (test gate) 和 `TaskCompleted` (full DoD)
3. **不要跳过 Conventional Commits**：这是自动 Changelog 和语义化版本的基础
4. **将 Spec 文件纳入仓库**：让 AI 可以随时对照需求验证实现
5. **监控 Hook 性能**：设置合理的 timeout，避免 hook 过慢影响开发体验

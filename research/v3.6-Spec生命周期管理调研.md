# Spec/设计文档生命周期管理 — 全面调研报告

*调研日期：2026-03-09 | 搜索语言：英文*

---

## 一、各大厂 / 社区的 Spec/RFC/Design Doc 状态流转

### 1.1 Google — Design Docs

流程阶段：Writing → Rapid Iteration → Review → Implementation

核心目的：早期发现设计问题、达成共识、确保跨领域考虑、扩展资深工程师的知识影响力、形成组织记忆。

> 来源：[Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/)

### 1.2 Uber — 从 DUCK 到 RFC 再到分级工程规划

- 早期：DUCK 格式文档
- 中期：RFC，增加 "approver" 字段
- 规模瓶颈：2000+ 工程师，每周数百份 RFC，噪声最大问题
- 后期：分级工程规划流程（Tiered Engineering Planning Process），专用工具集中存储

> 来源：[Scaling Engineering Teams via RFCs](https://blog.pragmaticengineer.com/scaling-engineering-teams-via-writing-things-down-rfcs/)

### 1.3 Phil Calcado 的 Structured RFC Process

中小团队最常采用的参考框架，明确的状态机：

| 状态 | 含义 |
|------|------|
| **Draft** | 撰写中，尚未请求广泛反馈 |
| **Discussion** | 已公开征求反馈 |
| **Development** | 实现进行中 |
| **Active** | 实现完成，方案生效中 |
| **Dropped** | 不再推进 |
| **Superseded** | 被更新的 RFC 取代 |

> 来源：[A Structured RFC Process](https://philcalcado.com/2018/11/19/a_structured_rfc_process.html)

### 1.4 行业综合对比

| 公司/框架 | 文档类型 | 核心状态 | 审批方式 |
|-----------|---------|---------|---------|
| Google | Design Doc | Write → Review → Implement | 评审会议 + 异步评论 |
| Uber | RFC → Engineering Plan | Draft → Review → Approved → Implementing | Approver 签字 |
| Stripe | Design Doc | Write → Review → Decide | 异步评审文化 |
| Phil Calcado | RFC | Draft → Discussion → Development → Active/Dropped/Superseded | 时间窗口 + 共识 |

## 二、ADR（Architecture Decision Records）最佳实践

### 2.1 ADR 标准格式

**MADR（Markdown ADR）4.0.0**（2024年9月）：

核心结构：**Context（背景）→ Decision（决定）→ Consequences（后果）**

> 来源：[MADR Official](https://adr.github.io/madr/)

### 2.2 ADR 状态

| 状态 | 含义 |
|------|------|
| **Proposed** | 草案，开放讨论中 |
| **Accepted** | 决定已做出 |
| **Deprecated** | 不再相关，保留历史 |
| **Superseded** | 被更新的 ADR 取代 |

> 来源：[AWS ADR Process](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)

### 2.3 ADR vs Spec

| 维度 | ADR | Spec/Design Doc |
|------|-----|-----------------|
| 粒度 | 单个架构决策 | 完整功能/系统设计 |
| 可变性 | Immutable（只能 supersede） | 可迭代修改 |
| 生命周期 | 长期存档（永久） | 有实效性（可归档） |
| 重点 | **Why**（为什么这么决定） | **What + How**（做什么+怎么做） |

## 三、AI 辅助的文档状态管理（2025-2026 爆发期）

### 3.1 SDD 工具生态

#### AWS Kiro IDE

三阶段工作流：requirements.md → design.md → tasks.md
特色：Agent Hooks（文件保存/创建/删除时自动触发 agent）+ Steering Files

> 来源：[Kiro Docs](https://kiro.dev/docs/specs/)

#### GitHub Spec Kit（v0.1.4, 2026-02）

GitHub 官方开源 SDD 工具包，支持 Copilot、Claude Code、Gemini CLI、Cursor、Windsurf。
使用 YAML frontmatter 管理文档元数据。

> 来源：[GitHub Spec Kit](https://github.com/github/spec-kit)

#### cc-sdd（Claude Code SDD）

专为 Claude Code 设计，自动进度追踪：Specified(20%) → Planned(40%) → Tasked(60%) → In Progress(80%) → Complete(100%)

> 来源：[cc-sdd](https://github.com/gotalab/cc-sdd)

#### OpenSpec

专注存量代码库演进（brownfield），两目录模型：openspec/specs/（当前状态）+ openspec/changes/（提议变更）
严格的软件演进状态机，四个不可逆阶段。

> 来源：[OpenSpec](https://openspec.dev/)

### 3.2 工具对比

| 工具 | 定位 | 状态自动追踪 | 适用场景 |
|------|------|-------------|---------|
| Kiro | 全功能 IDE | 原生支持 | 新项目 |
| GitHub Spec Kit | 工具包 | 半自动 | GitHub 团队 |
| cc-sdd | Claude Code 插件 | 自动进度% | Claude Code 用户 |
| OpenSpec | 轻量框架 | 状态机驱动 | 存量代码库 |

## 四、Spec 与代码的关联方式

| 方法 | 优点 | 缺点 |
|------|------|------|
| Commit message reference | git log 可追踪 | 事后难聚合 |
| YAML frontmatter（记录关联 PR/commit） | 结构化、可机器解析 | 需工具更新 |
| 目录共存（spec 与代码同仓库） | 版本同步、原子提交 | 仓库体积增大 |

### 归档策略

- 标记状态而非移动文件（改为 implemented，保留原位）
- Supersede 而非删除（新版指向旧版）
- ADR 永不删除（永久历史记录）

## 五、推荐方案：适合中小团队 + AI 协作的简化版

### 5.1 状态流转

```
draft → in-review → approved → implementing → implemented → [deprecated | superseded]
                  ↘ rejected
```

| 状态 | 触发条件 | 谁来标记 |
|------|---------|---------|
| draft | 创建 spec | 作者 |
| in-review | 提交评审 | 作者 |
| approved | 评审通过 | 评审人 |
| rejected | 评审不通过 | 评审人 |
| implementing | 开始编码 | AI agent 自动 |
| implemented | 功能完成 | AI agent 自动 |
| deprecated/superseded | 技术变化/新 spec | 团队成员 |

### 5.2 推荐文件格式（YAML Frontmatter）

```yaml
---
id: SPEC-2026-003
title: User Authentication Redesign
status: implementing
type: feature-spec            # feature-spec | adr | rfc
author: alice@team.com
created: 2026-02-15
updated: 2026-03-05
related_prs: ["#142", "#158"]
tags: [auth, security]
---
```

### 5.3 AI 协作集成

**轻量级方案（推荐起步）**：在 CLAUDE.md 中添加规则：
- 开始实现 spec 功能时，自动将 status 更新为 "implementing"
- 完成后自动更新为 "implemented"，补充 related_prs
- Commit message 引用：`Ref: SPEC-2026-003`

## 六、关键结论

1. **状态管理是刚需**：所有达到一定规模的团队都需要明确的文档状态流转
2. **2025-2026 是 SDD 爆发期**：Kiro、Spec Kit、cc-sdd、OpenSpec 密集出现
3. **ADR 和 Spec 应共存**：ADR = Why（不可变），Spec = What+How（可迭代）
4. **YAML Frontmatter 是事实标准**：所有主流工具都采用
5. **中小团队建议**：Markdown + YAML Frontmatter 起步，CLAUDE.md 规则自动遵守
